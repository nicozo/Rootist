# Context7 の導入効果の計測

issue #127。Context7（Docker MCP Gateway 経由。`mcp__MCP_DOCKER__resolve-library-id` / `mcp__MCP_DOCKER__query-docs`）を generator に付与した効果を、**継続／使用ルール改善／撤去**の判断に使える形で測るための手引き。

- **A. 観察ログ**（実装済み）: 使用場面の明文化、`self_evaluation.md` への使用記録、集計スクリプト、台帳（[context7-ledger.md](./context7-ledger.md)）。
- **C. 狙い撃ち比較**（整備のみ）: 固定課題・判定基準・結果表・実施手順は [context7-benchmark/](./context7-benchmark/README.md)。**あり／なしの実測は本 issue では実施していない。実測は別 issue で行う**。
- 継続／改善／撤去の判断も本 issue では下していない。下記の判断マトリクスと「判断の記録様式」で、データが溜まった時点で下す。

| 正確性     | 申告のバージョン一致区分、採用結果の区分                                       | 廃止・存在しない API の使用有無、バージョン一致 |
| 運用コスト | 障害件数（接続失敗・キー失効・レート制限）                                     | 同左＋実施時のセットアップ手間（分）            |

## 集計の実行方法

```bash
pnpm metrics:context7 -- --dir ~/.claude/projects/-Users-katoukouhei-Dev-rootist/ --dev-loop /Users/katoukouhei/Dev/rootist/.dev-loop
```

- Node 標準のみ（追加依存なし）。TypeScript を Node の型除去（type stripping）で直接実行する。必要な Node は **22.18 以上**（`--experimental-strip-types` 無しで既定有効になった版。v22.18.0 / v23.6.0 から。出典: https://nodejs.org/api/typescript.html 。**実機で動作確認したのは v24.11.1 のみ**）。
- pnpm は script 名の後ろの `--` をそのまま渡すが、CLI は先頭の `--` を取り除いて解析する（`--dir` が位置引数として無視され、既定ディレクトリが黙って使われることはない）。
- 読み取り専用。セッション記録・`.dev-loop` を書き換えない。

| オプション                                      | 意味                                                                                                                                                                                                                                                      |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--dir <path>`                                  | セッション記録ディレクトリ（複数指定可。既定 `~/.claude/projects/-Users-katoukouhei-Dev-rootist/`）。直下の `*.jsonl`（メイン）と `<session-id>/subagents/agent-*.jsonl`（サブエージェント。同名 `.meta.json` の `agentType` で種別を決める）の両方を読む |
| `--dev-loop <path>`                             | `.dev-loop` ディレクトリ（`self_evaluation.md` の突合に使う）。省略時はメインのワーキングツリー直下の `.dev-loop/`（無ければ突合しない）                                                                                                                  |
| `--issue <N>`                                   | issue 番号で出力を絞る（ワークスペースの紐付けは全体で行ってから絞る）                                                                                                                                                                                    |
| `--since <YYYY-MM-DD>` / `--until <YYYY-MM-DD>` | 期間（UTC の日付）で行を絞る                                                                                                                                                                                                                              |
| `--format md\|json`                             | 出力形式（既定 md）                                                                                                                                                                                                                                       |
| `--calls`                                       | 呼び出し一覧（クエリは先頭 60 文字のみ）も出す                                                                                                                                                                                                            |

存在しない `--dir` はエラーメッセージを出して終了コード 2 で終わる。壊れた行・途切れた行・`meta.json` の欠落はその行・ファイルだけをスキップし、件数を警告に出す。呼び出しが 1 件も無い入力は空の表を出す（エラーにしない）。

| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| issue                    | issue 番号。`issue 不明` はブランチに `issue-<N>` が無い行（main 等）、`issue 不明（要確認）` は QA レポートの書き込み先ワークスペースとブランチが食い違った行、`ベンチ` は `bench/c7-` ブランチの行（C の実施用）                                                                                                                                                                   |

| generator 呼び出し       | そのうち generator サブエージェントの呼び出し数（「付与したのに使っていない」を見る）                                                                                                                                                                                                                                                                                                |

### 警告の意味

| 警告                                | 意味                                                                                                                                                                                           |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 申告との不一致                      | 節あり。「使用ありと申告したのに実績 0」または「使用なしと申告したのに実績あり」。記録義務の書式・evaluator の確認観点を見直す材料                                                             |
| 使用記録なし                        | 節なしなのに Context7 の実績がある。記録義務が守られていない                                                                                                                                   |
| スラッグ不一致                      | ワークスペース名のスラッグとブランチのスラッグが完全一致しない（ブランチに `issue-<N>` が無い場合を含む）行からの参照。**ワークスペース単位に 1 件にまとめて**出す。その参照は紐付けに使わない |
| 旧形式の qa_report.md               | iter 番号の無い QA レポート。イテレーション・FAIL は不明（旧形式）                                                                                                                             |
| 使用記録: ファイル無し / 紐付け不能 | 上の表のとおり                                                                                                                                                                                 |
| 読めない行 / meta.json 欠落         | 壊れた入力をスキップした件数                                                                                                                                                                   |

### 台帳

[context7-ledger.md](./context7-ledger.md) に issue 別の 1 行サマリを蓄積する。理由: Claude Code は `cleanupPeriodDays`（ローカルの会話記録を何日で消すか）でセッション記録を削除する。公式ドキュメント（https://code.claude.com/docs/en/data-usage 、2026-10-04 に取得）は「`~/.claude/projects/` に 30 日（既定）」と述べ、`cleanupPeriodDays` で調整できるとする。このリポジトリの環境では `~/.claude/settings.json`・`.claude/settings*.json` に明示設定は無かった（取得時点で最古の記録は 2026-08-25 のもので、既定の 30 日より古い記録が残っていた）。5〜10 issue 溜まる前に初期の記録が消えうる（worktree 内の `.dev-loop` も cleanup で消える）ので、**集計結果の要約をリポジトリに残す**。台帳の行は手で書かず、集計スクリプトの出力から転記する。台帳には件数・ライブラリ名・判定結果のみを書き、プロンプトやツール結果の本文は書かない。

## 誤読しやすい点

- **A の比較は相関であって因果ではない**。issue の性質（UI のみ／DB 変更あり／認証など）で QA の差し戻し回数は大きく変わる。サンプル数が少ないうちは傾向の確認にとどめる。
- **所要時間は作業時間ではない**。QA 待ちや夜間の空き時間が含まれる（generator の記録ファイルの最小〜最大の差のため）。
- **サブエージェントの cwd がメインのワーキングツリーだと、`gitBranch` が実際の作業先とずれる**。例: evaluator の cwd がメインにあり、別 issue のブランチ名が記録された例がある。QA レポート・自己評価の紐付けはワークスペース名とブランチ名のスラッグ照合で防いでいるが、**Context7 の呼び出しの紐付けは行の `gitBranch` だけ**で、同じ危険がある。1 つのセッションが途中でブランチを変えるため、ファイル単位ではなく行単位で紐付けている。
- **導入前の issue の QA 回数は `不明（旧形式）`**。導入前は `qa_report.md`（iter 番号なし）に書いていたため、0 回（差し戻し無し）と読んではいけない。導入前後の品質比較には使えない。
- 使用場面ルールを改訂したら、台帳の備考に版を記録し、改訂前後を混ぜて比較しない（初期データは全て使用場面ルール v0 =「迷ったら」の時期）。

## あり/なしの傾向比較の手順（目安: 該当場面ありの issue が 5〜10 件溜まった時点）

1. 集計を実行し、台帳を最新化する。
2. 「該当場面あり」の issue（`self_evaluation.md` の `該当場面: あり`）だけを対象に、「query-docs ≥1」群と「0」群に分ける。
3. 群ごとに QA イテレーション数・FAIL 回数・トークン・所要時間の中央値と件数を並べる。
4. 利用率と、未使用理由の区分の内訳（特に `記憶で書けると判断した`）を確認する。
5. 障害件数を確認する。
6. 下の判断マトリクスに当てはめ、結論と根拠を下の様式で台帳の備考または判断記録に残す。

## 判断マトリクス

版: **v1**（閾値は初期値。改訂するときは版を上げて理由を残す）。A と C を合わせて見る。

| 状況（A と C を合わせて見る）                                                                           | 判断               | 次のアクション例                                                                       |
| ------------------------------------------------------------------------------------------------------- | ------------------ | -------------------------------------------------------------------------------------- |
| 利用率が高い（目安 60% 以上）かつ C で「あり」の正答率が明確に高い、または A で使用群の差し戻しが少ない | **継続**           | 現行ルール維持、定期集計を続ける                                                       |
| 利用率が低い（目安 30% 未満）が、C で「あり」の正答率が明確に高い                                       | **使用ルール改善** | 使用場面の必須条件を強める、プロンプトでの指示を具体化し、改訂版として再計測           |
| 申告と実績の不一致が多い                                                                                | **使用ルール改善** | 記録義務の書式・evaluator の確認観点を見直す                                           |
| C で正答率に差が無い（または「なし」が同等以上）、かつ障害・運用コストが無視できない                    | **撤去**           | generator のツールから外し、プロファイル・シークレット・docs を片付ける別 issue を起票 |
| データ不足（該当場面ありの issue が 5 件未満、または C 未実施）                                         | **保留**           | 計測継続。撤去・継続の判断はしない                                                     |

- 「明確に高い」の定義（v1）: C で、課題あたりの正答数が「あり」の方が「なし」より **2 以上**多い（課題 4 つ × 3 試行 = 12 試行なら合計の正答数の差 2 以上）。実施規模が変わったら定義を見直して版を上げる。
- 使用ルールを改訂したら台帳の備考に版を記録し、改訂前後を混ぜて比較しない。

## 判断の記録様式

判断を下したら、次の項目を台帳の備考、または判断記録（`docs/` 配下に日付付きで 1 件 1 ファイル）に残す。

| 項目           | 内容                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| 日付           | 判断した日（UTC）                                                                                      |
| 対象期間       | 台帳の行の範囲（issue 番号または日付）、使用場面ルールの版                                             |
| 件数           | 該当場面ありの issue 数、query-docs ≥1 群・0 群の件数、C の試行数                                      |
| 各指標         | 利用率、QA イテレーション・FAIL の中央値、トークン・所要時間の中央値、不一致件数、障害件数、C の正答率 |
| 結論           | 継続／使用ルール改善／撤去／保留（判断マトリクスのどの行か）                                           |
| 次のアクション | 具体的な作業（別 issue の番号を含む）                                                                  |
