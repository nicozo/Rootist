# issue-writer

要望や課題感を、なぜ・何を・開発要件・完了条件で構成されたGitHub issueに仕上げる。目的はテンプレートを埋めることではなく、**起票前に背景を本人と一緒に固めること**。曖昧な「なぜ」のまま起票すると、後工程（設計・実装）が的外れな解決策を作ってしまう。

## 進め方

1. **なぜ（背景）を深掘りする — 必須**
   最初の説明が「何が欲しいか」で止まっているなら、その背後の動機を尋ねる。目安になる問い:
   - 何がきっかけでこの話が出てきたか（具体的な出来事・観察・不便）
   - 今のままだと何が困るか。困っていないなら、なぜ今やる価値があるのか
   - 答えが「何を」の言い換えになっているだけなら（例:「なぜ: ○○が欲しいから」）、一段掘り直す

   ユーザーの回答が具体的になるまで確認を続けること。ただし既に本人が背景を具体的に語っている場合は、同じ質問で冗長に繰り返さない — 深掘りの必要性は状況で判断する。掘り下げた内容は自分の言葉で要約し、認識が合っているか本人に確認してから次に進む。

2. **何を（要望）を1〜3文に凝縮**
   深掘りで見えた背景を踏まえ、実現したいことを簡潔に言い直す。ユーザー自身の言葉から離れすぎないこと。

3. **開発要件を「満たすべきこと」として書き出す**
   実装手段ではなく、満たすべきことを箇条書きにする。「〜できること」「〜が表示されること」「〜の場合は〜しないこと」のように、**外から観察できる状態**で書く。

   書いてはいけないもの — 技術選定、ファイル構成、関数・コンポーネントの分割方針、アルゴリズムやデータ構造の指定。これらは設計・実装フェーズの仕事であり、issueで先回りすると実装者の判断余地を奪う。手段が浮かんだら「それによって何が満たされるのか」に言い換えてから書く。

   ユーザーが手段の形で語った場合はそのまま転記せず、要件の形に翻訳して確認を取る。

4. **完了条件は固定**
   完了条件セクションは常に次の1行だけにする。要件ごとに分解したりしない（分解すべきなら開発要件側の粒度を直す）。

   ```markdown
   - [ ] 上記「開発要件」をすべて満たしている
   ```

5. **下書きを見せてから起票する**
   `gh issue create` はGitHub上に公開される行為。下書きを提示し、ユーザーの了承を得てから実行する。

## テンプレート

`.github/ISSUE_TEMPLATE/feature_request.md` の構成（なぜ／何を／開発要件／完了条件／補足）に従う。

## 実行

`gh issue create --label enhancement --title "..." --body "..."` で作成し、発行されたissue URLを報告する。
