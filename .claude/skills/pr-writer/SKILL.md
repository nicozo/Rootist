# pr-writer

現在のブランチの差分から、レビュワーが「何を」だけでなく「なぜそう実装したか」まで追えるPRを作成する。目的はdiffの要約ではなく、**レビュワーの理解コストを下げること**。

## 進め方

1. **差分と経緯を集める**
   `git status` / `git diff <base>...HEAD` / `git log <base>..HEAD` でベースブランチとの差分・コミット履歴を確認する。紐づくissueがあれば `gh issue view` で背景を取得する。`.dev-loop/<slug>/` にspec.mdやdecision_iter\*.mdが残っていれば、実装判断の記録として参照する。

2. **なぜ（目的）**
   紐づくissueの「なぜ」を1〜2文に要約する。issueが無い、または薄い場合はユーザーに確認する。

3. **何を（変更の要約）**
   ファイル名やdiffの羅列ではなく、**変更後に何がどう変わるか**を結果視点で書く。「〜を追加した」ではなく「〜ができるようになった」「〜が起きなくなった」。

4. **どうやって（実装アプローチ）— このPRの主眼**
   レビュワーが意図を掴めるように書く:
   - 採用したアプローチと、検討した代替案があればその比較
   - 非自明な実装判断（一見遠回り・トリッキーに見える箇所）とその理由
   - 変更の構造（主要ファイルの役割、処理の流れ）

   diffを読んで説明が要ると感じた箇所は、憶測で埋めずユーザーに意図を確認してから書く。

5. **下書きを見せてからpush・PR作成する**
   pushとPR作成は公開行為。下書きを提示し、ユーザーの了承を得てから実行する。PR作成と同時にauto-mergeを有効にする旨も下書きと一緒に伝える（了承はまとめて得てよい）。

## テンプレート

`.github/pull_request_template.md` の構成（なぜ／何を／どうやって／影響範囲・契約／検証／レビュー観点／補足）に従う。「影響範囲・契約」「検証」は既存の型を維持する（API/state/挙動の非破壊性、pnpm check/lint/testの実行有無）。

## 実行

`gh pr create --title "..." --body-file -`（またはヒアドキュメント）で作成し、続けて auto-merge を有効にする。

```bash
gh pr merge <PR番号> --auto --merge
```

- auto-merge は「必須ステータスチェック・必須レビューが揃うまで待ってからマージ」する仕組み。ベースブランチに必須チェックが無いとCIを待たずに即マージされるため、有効化の前に `gh api repos/{owner}/{repo}/branches/<base>/protection` でブランチ保護（必須ステータスチェック）があるか確認する。無ければ auto-merge は有効にせず、その旨をユーザーに伝える。
- マージ方式はリポジトリの慣習に合わせて merge commit（`--merge`）を使う。
- 発行されたPR URLと、auto-mergeを有効にしたかどうかを報告する。

## マージ後の後片付け

PR作成後、`cleanup` スキルを PR番号付き（監視モード）で呼び、マージを見守る。マージされたら自動でマージ済みローカルブランチが片付く。auto-merge を有効にしなかった場合も、手動マージを拾うため同様に監視する。
